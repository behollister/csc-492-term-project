# Glossary

This page defines terminology used throughout the project. Entries should be concise, written for a computer science reader who may not know the project domain, and updated as the project evolves.

## Project terms

| Term | Definition |
|---|---|
| **Architecture** | The high-level organization of a system, including its components, their responsibilities, and the ways they communicate. |
| **API (Application Programming Interface)** | A defined interface through which software components request data or operations from one another. |
| **Background study** | Research performed to understand the problem domain, relevant literature, existing systems, and available technical approaches. |
| **Capstone project** | A culminating undergraduate project in which students apply knowledge from their degree program to a substantial problem. |
| **Functional requirement** | A behavior or capability the completed system must provide. |
| **Non-functional requirement** | A quality or constraint on the system, such as security, performance, accessibility, reliability, or maintainability. |
| **Node.js** | A JavaScript runtime used to execute server-side application code outside a web browser. |
| **REST** | An architectural style for networked applications that commonly models data as resources accessed through standard HTTP methods. |
| **Prototype** | An early implementation used to explore feasibility, requirements, or design choices. |
| **Research question** | A focused question used to guide investigation and evaluate relevant evidence. |
| **Scope** | The boundary identifying what the project will and will not address. |
| **Stakeholder** | A person or group that affects, uses, evaluates, or is affected by the project. |
